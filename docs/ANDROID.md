# Android

ClefGlide uses the same React/Vite application on the web and in an Android Capacitor WebView. Capacitor copies the existing `dist/` production build into the APK; it does not load the hosted website. Virtual-piano practice works without a MIDI device. Optional USB and Bluetooth Low Energy MIDI input use Android's native MIDI service. iOS is not supported.

## Run on your phone from Windows

Use Node.js 24 and Android Studio 2025.2.1 or newer. In Android Studio's SDK Manager, install Android SDK Platform 36 and the SDK build/platform tools. Use Android Studio's bundled JDK 21 for Gradle. The app supports Android 7.0/API 24 or later with a current Android System WebView.

From the repository root:

```powershell
npm ci
npm run android:sync
npm run android:open
```

On your phone, enable **Developer options → USB debugging**. Connect it to the PC with a data cable, unlock it, and accept the debugging prompt. In Android Studio, wait for Gradle sync, select your **physical phone** and the **app** run configuration, then press **Run**. No emulator is needed. Select **Start practice** and open **Virtual piano** to try the shared application first.

Once installed, disconnect the PC and connect a class-compliant USB MIDI keyboard using a suitable USB-C/OTG adapter (and a powered hub if the keyboard needs it). ClefGlide automatically discovers USB MIDI on startup, attachment and foreground resume, without Bluetooth permissions. One usable USB sending port connects automatically while practice is idle and no input is selected. With multiple ports, choose one in the MIDI device dropdown beside the Bluetooth button. Android has no manual **Connect MIDI** button; the website retains its user-triggered permission flow. Press **Start practice** when ready. The app stays installed and runs locally without the PC or a server.

For Bluetooth, enable Bluetooth in Android settings and enable BLE-MIDI advertising on the piano or MIDI adapter. Tap the Bluetooth icon (**Discover Bluetooth MIDI**) beside the input dropdown, or the full button in **Settings & help**. Grant the requested permission, wait up to 10 seconds, and choose the entry marked **(Bluetooth MIDI)** in the existing MIDI input picker. Then press **Start practice**. Bluetooth audio and ordinary pairing alone do not supply MIDI notes. No connector app is needed in the native app; browser connection instructions remain separate.

Discovery alone never selects a Bluetooth piano or replaces a selected input. If Android pauses the Activity to show a permission dialog, the normal pause cleanup closes the selected input. Selecting a different input closes the old input first: only one sending port is active. Bluetooth uses the device's first sending port. USB reconnects automatically on foreground resume or reattachment when only one port is usable and practice is idle; multiple ports require selection. Bluetooth reconnection always requires discovery and selection. A selected input is never replaced automatically; an explicit deselection or Bluetooth choice also blocks USB auto-selection until the next foreground cycle. A failed USB auto-open is attempted once per device presence/foreground cycle; choose the input to retry, reconnect its cable, or background/resume. Automatic selection never starts practice and is skipped while virtual practice is running; a connection completing during practice pauses it before switching input. Devices must advertise the standard BLE-MIDI service; proprietary Bluetooth protocols are not supported. Scan results and addresses stay in memory and are cleared on backgrounding, with no persistent device pairing preference.

Bluetooth permissions are requested **only when tapping Discover Bluetooth MIDI**, never at startup, Connect MIDI/USB, selection or resume. Android 12+ requests Nearby devices (`BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT`), with `neverForLocation`; ClefGlide does not infer location. Android 7–11 requires Location permission and enabled Android Location services for BLE scanning; legacy Bluetooth permissions and Location are capped at API 30. No advertising, background location or background scanning permissions are requested. If denied, enable the permission in Android app settings and retry discovery; USB and virtual input remain available. If Bluetooth is off or unsupported, the app reports it without enabling the radio automatically.

Scans stop after 10 seconds, when selecting a Bluetooth input, or when leaving the foreground. USB and Bluetooth opens time out after 15 seconds. A failed scan or connection can be retried explicitly. Closing, switching, disconnecting and backgrounding invalidate outstanding opens; late devices are closed and stale packets are discarded. Returning to the app never resumes scoring automatically. An Android permission dialog may briefly pause the Activity; its result starts scanning only after foreground resume, and an actual background transition cancels it.

Connection buttons contain a subtle spinner during permission requests, scanning and Bluetooth connection; duplicate attempts are disabled. A small inline indicator beside the MIDI controls shows idle, pending, connected or failed state. Detailed messages remain available on hover and as a polite screen-reader status, without a separate text row or progress percentages. Reduced-motion preferences keep the loading icon static. Buttons recover on completion, denial, cancellation, scan failure/timeout or connection timeout. Scanned inputs can be selected while scanning; selection stops the BLE scan when opening Bluetooth.

After changing web code, run `npm run android:sync` again before running from Android Studio. After changing only Kotlin, rebuild/run in Android Studio. Keep `org.clefglide.app` and Capacitor's local origin stable so updates retain the app's IndexedDB data.

If `android:open` cannot find a nonstandard Android Studio installation, open the `android/` folder from Android Studio directly, or set `CAPACITOR_ANDROID_STUDIO_PATH` to the full path of `studio64.exe`.

For command-line builds, set `JAVA_HOME` to your JDK 21 and `ANDROID_HOME` to your SDK directory, then run:

```powershell
npm run android:sync
.\android\gradlew.bat -p android :app:assembleDebug :app:testDebugUnitTest
```

The debug APK is `android/app/build/outputs/apk/debug/app-debug.apk`. Release signing and Play Store publication are separate tasks. Signing keys and local SDK configuration are ignored by Git.

If using the optional workspace Node installation, follow [the Windows fallback](DEVELOPMENT.md#windows-workspace-fallback). The equivalent sync is `npm run build` with that npm entry point followed by `.tools/node.exe node_modules/@capacitor/cli/bin/capacitor sync android`; Android Studio can open `android/` directly.

## MIDI and lifecycle architecture

- `src/midi/adapter.ts` retains `MidiBus`, `MidiEvent` and the WEBMIDI.js adapter. `MidiAdapter` exposes enable, input selection, selected input, disposal and an optional native Bluetooth discovery capability; construction never requests MIDI access. The browser adapter has no Bluetooth discovery implementation.
- `src/midi/platform.ts` selects WEBMIDI.js in browsers and `AndroidMidi` on Android. Shared React practice, generation, notation, scoring and progress use the same contracts. A future native adapter can extend this selection without changing scoring.
- `src/midi/android.ts` subscribes to the local `NativeMidi` Capacitor plugin. Kotlin's `NativeMidiPlugin` enumerates USB MIDI 1.0 byte-stream output ports and combines them with discovered Bluetooth entries in the same picker. Android calls these **output** ports because the keyboard sends data to the app. No SysEx request is made.
- `BluetoothMidiManager.kt` isolates permission policy, foreground scanning, radio/disconnect broadcasts, connection timeouts and stale BLE callback cleanup. A scan filter uses the standard MIDI service UUID `03b80e5a-ede8-4b33-a751-6ce34ec4c700`; advertisements are checked and deduplicated by address. It opens selected devices through `MidiManager.openBluetoothDevice()`. Android decodes BLE-MIDI transport framing and timestamps, then the plugin attaches the same receiver/parser used for USB. There is no custom GATT/protocol parser or third-party Bluetooth dependency. Capacitor permission declarations/callbacks remain bridge glue in the plugin.
- `MidiStreamParser` decodes note-on/off, velocity-zero note-off and CC64 sustain, including running status and messages split across callbacks. Other controllers, system messages and SysEx payloads are ignored. Channels stay 1–16 and C4 stays MIDI 60. Native monotonic timestamps are calibrated to `performance.now()` through a short clock round trip rather than using JS delivery time; actual device and bridge latency still need measurement.
- Pause closes the selected port/device, unregisters discovery and invalidates pending opens and queued MIDI packets. The lifecycle listener pauses shared practice even with virtual input. Resume refreshes USB discovery and may connect a sole USB port, using the existing listener registration; press **Start** manually. Removal closes the port and pauses practice. Disposal removes JS listeners and stops discovery; Activity destruction also releases native resources. Connection generations reject stale packets/callbacks after switching, pausing or disconnecting. Additive `phase`/`pendingId` state metadata drives loading feedback; MIDI message fields and timestamp handling are unchanged.

The app keeps the existing IndexedDB schema, export format and import validator. Android's WebView has its own local storage, separate from Chrome's website data; use JSON export/import to transfer history. App uninstall/data clearing removes local history. Android automatic cloud backup is disabled. `src/platform/download.ts` keeps the original browser download function and uses the local `ProgressFiles` plugin on Android to save identical JSON/CSV through the system document picker, without storage permissions. Imports use Capacitor's WebView file chooser and the existing importer.

The Vite web build, browser persistence implementation and deployment configuration remain unchanged.

## Verification and phone checks

### System bars and edge-to-edge layout

Capacitor 8.6.2's `SystemBars` uses `insetsHandling: "native"` with `initialViewportFitValueHint: "cover"`. `MainActivity.java` calls AndroidX `EdgeToEdge.enable`; the active WebView is Capacitor's match-parent bridge layout, not the unused template `activity_main.xml`. Android startup adds `viewport-fit=cover` before React mounts. The browser viewport remains unchanged.

The previous viewport omitted `cover`, so Capacitor padded the native decor and shortened the WebView. The resulting full-width native strip could never display the webpage's sidebar, regardless of its background color. The page also had no main-column safe-area spacing. `src/platform/android.css` now applies measured `env(safe-area-inset-*)` values inside the sidebar and main column, leaving their backgrounds edge-to-edge. The sidebar retains its existing responsive design padding; the phone header alone clears the top inset. The existing full-screen range dialog already handles safe areas. No root/body inset or additional native inset listener is added. Navigation bars are transparent where dark navigation icons are supported; system indicators remain visible.

WebView 140 or newer is required for this full edge-to-edge path. On older WebViews, Capacitor deliberately retains native padding and reports zero CSS insets; this avoids double compensation but can retain a native border. Update Android System WebView/Chrome before checking edge-to-edge behavior. See [Capacitor's SystemBars documentation](https://capacitorjs.com/docs/apis/system-bars).

Browser regression tests simulate changing safe-area values across portrait/landscape phones, tablets and both themes, including zero-inset fallback. They check sidebar coverage, heading clearance, footer accessibility and unchanged regular-web spacing. Physical verification must still cover actual inset delivery, screen cutouts, status/gesture indicator contrast, gesture and three-button navigation, rotation, keyboard open/close, and light/dark switching. No emulator or phone run is implied by browser simulations or an APK build.

Android's app shell stays viewport-sized; its main column owns vertical scrolling with `overscroll-behavior-y: contain`. The rail is outside that scroll container, including the horizontal phone header, so main-content boundary gestures cannot stretch the shared document and navigation. Regular web pages and the separate legal-notice route keep document scrolling. A browser regression checks actual wheel scrolling, bottom-boundary containment, stable rail geometry and working navigation; the Android stretch animation itself still needs a physical-device swipe check.

`npm run typecheck`, `npm run lint`, `npm run test`, `npm run test:e2e` and `npm run build` cover the shared application. `:app:testDebugUnitTest` runs Kotlin parser tests and mocked Android tests for USB discovery, BLE UUID filtering/deduplication, permission gating and denial, scan/open timeouts, radio loss, lifecycle cleanup, stale callbacks, USB/BLE switching, chords, sustain and preserved timestamps. TypeScript tests exercise USB auto-selection, foreground refresh, manual choices, failed-open retry limits, stale clock replies and BLE selection through the existing bus. Playwright simulates native progress phases, button recovery, reduced motion and the website's click-only permission flow. These are simulations: they do not run Android's permission UI, Bluetooth radio, MIDI service transport or a physical keyboard. No Android emulator is needed for these unit tests. An APK build establishes compilation/packaging, not hardware operation.

On your physical phone, verify:

- Virtual-piano touch input, notation, timed/count-in mode and metronome. Background or lock the phone while practicing; confirm practice pauses and does not restart by itself after returning.
- Connect an actual USB MIDI keyboard before launch, on the practice screen, and while backgrounded. Confirm discovery on launch/attachment/resume, automatic selection only for a sole port while idle, manual selection for multiple ports, and no Connect MIDI button. Attach while virtual practice is running: it must not change the active input. Verify that reconnecting never starts practice. Check C4, other registers, channels, repeated/held notes, chords and velocity-zero note-off.
- Press/release sustain, release notes while holding the pedal, and repeat notes. MIDI checks pitch/timing, never which human finger was used.
- Unplug while holding notes/pedal; practice must pause with a disconnect message. Replug, select/reconnect and manually start; there must be no stuck keys, duplicate subscriptions or stale note attacks. Repeat while backgrounding/resuming the app and while a connection is opening.
- On Android 12+ and Android 7–11, verify that startup, USB attachment/automatic selection and resume show no Bluetooth permission prompt. Tap discovery; deny, retry, grant, and test permanent denial/revocation in settings. Confirm visible permission/scan/connection status, spinner behavior, duplicate-attempt prevention and button recovery after denial/cancellation/timeout. On older Android also test Location services off/on. Verify Bluetooth unsupported/off, scan failure/empty timeout, and a piano that disappears or refuses connection. With reduced motion enabled, loading icons should remain static.
- With a real standard BLE-MIDI piano/adapter, discover/select and check C4, channels, note-on/off, velocity-zero note-off, repeated and held notes, chords, sustain on/off and released notes under sustain. Compare native event timing/latency with the actual instrument. Neither packet/parser simulations nor an APK build verify BLE framing, device compatibility or timing quality.
- Switch USB → Bluetooth → USB while notes/pedal are held; ensure one active input, cleared held state, no duplicate events and manual practice restart. Turn the piano or phone Bluetooth off during scanning, opening and practice; background/lock during each phase. Restore, rediscover and explicitly select/start. Repeat rapid switches and delayed connections to check stale callbacks and reconnection without stuck notes.
- Save real outcomes, force-close/reopen the app, then export JSON and CSV through the file picker. Reimport the JSON and verify outcomes/history/settings. Cancel a file picker and retry. Browser and app backups must retain comparable fingerprints without mixing legacy results.
- Test long timed sessions and input latency against the actual keyboard. An APK build and simulated tests do not establish native WebView behavior, hardware compatibility, latency or comfortable human fingering.
